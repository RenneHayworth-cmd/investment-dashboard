# 第三章 运行时与缓存内核：core.paths / core.db / core.cache

## 理论

个人量化系统最常见的死法不是策略亏钱，而是**数据悄悄坏掉**：并发写坏 CSV、半截文件被当成完整历史、缓存被旧数据覆盖。内核层（`core/`）的职责就是把"写一个文件"变成一个**事务**：要么完整成功，要么保留旧值，且并发安全。

本项目内核只有四个文件、不到 500 行，却承担了全系统所有数据的落盘：

| 文件 | 行数 | 职责 |
|---|---|---|
| `core/paths.py` | 22 | 运行时目录解析（Windows→`~/investment_dashboard_data`，Linux→仓库根） |
| `core/db.py` | 374 | SQLite 连接、12 张表的建表/迁移、任务记录 |
| `core/cache.py` | 173 | 数据集（CSV+元数据）的事务性读写 |
| `core/indicators.py` | 13 | MA20 与偏离率的最小实现 |

## 数学原理

缓存一致性这里没有高深数学，但值得写清**原子替换**的正确性论证：写方先写临时文件 `X.tmp`，`os.fsync` 刷盘，再加文件锁复制旧文件为 `X.backup`，然后 `os.replace(X.tmp, X.csv)`。`os.replace` 在 POSIX 上是原子操作，因此任何时刻观察者看到的 `X.csv` 要么是旧的完整版，要么是新的完整版，不存在中间态。SQLite 侧再用 UPSERT 记录元数据，若元数据写入失败则把 CSV 回滚为 backup（`core/cache.py:123-129`）——这是"文件系统 + 数据库"两阶段提交的简化版。

## 当前项目实现

### 路径解析（core/paths.py）

```python
if os.name == "nt":
    RUNTIME_DIR = Path.home() / "investment_dashboard_data"
else:
    RUNTIME_DIR = ROOT_DIR
```

Windows 上数据与代码分离（代码在 `Documents/investment-dashboard`，数据在用户目录），Linux/WSL 上数据就在仓库根的 `data/`、`output/`、`cache.db`（均 gitignore）。

### SQLite 表清单（core/db.py）

业务表 12 张：`datasets`（数据集元数据，唯一键 `(symbol, source, data_type, period)`）、`jobs`（任务记录）、`correlation_results`（相关矩阵历史）、`live_trades`（ETF 实盘成交，含 `record_key UNIQUE` 幂等键）、`live_cash_flows`、期货实盘 7 张：`futures_statement_imports`、`futures_account_monthly`、`futures_month_end_positions`、`futures_live_trades`（部分唯一索引 `(source_file, asset_type, broker_trade_id) WHERE source='月结单' AND broker_trade_id IS NOT NULL`）、`futures_daily_closes`、`futures_cash_flows`、`futures_option_expiry_events`、`futures_daily_pnl_overrides`。

迁移用 `PRAGMA table_info` 探测列再 `ALTER TABLE ADD COLUMN`（如 `live_trades.trade_time`、`futures_account_monthly.declaration_fee`、`futures_daily_closes.settlement_price/settlement_source`）——对个人项目足够，且幂等。

### 数据集事务（core/cache.py）

- **锁守卫**（第 14-17 行）：`try: import fcntl / except ImportError: fcntl = None`——Windows 下退化为无跨进程锁的占位实现（`_dataset_lock` 直接 yield，注释说明"Streamlit 单进程部署下无需跨进程锁"）。这是写作本手册期间刚进入工作区的未提交修改；三个守护脚本仍直接顶层 `import fcntl`。
- `save_dataset(symbol, name, source, data_type, df, period)`（第 58 行起）：临时文件→fsync→文件锁（POSIX `fcntl.flock` 排他锁，锁文件为 `X.csv.lock`）→备份→`os.replace`（第 96 行）→SQLite UPSERT；失败回滚。
- `load_dataset(...)`（第 147 行起）：共享锁→查元数据→`status=='success'` 且文件存在才返回 DataFrame；否则 `(None, meta)`，meta 里仍带 `last_trade_date/last_update_time` 供 UI 显示"缓存时间戳"。
- `latest_trade_date_text(df)`：按 `trade_date/日期/date/datetime` 列顺序探测最新日期，写进元数据。

## 代码分析

逐段看 `save_dataset`（`core/cache.py:58` 起）的关键行：

- 函数入口处 `last_trade_date = latest_trade_date_text(df)` 在进入临界区**之前**计算——纯内存操作，缩短持锁时间；
- `with _dataset_lock(lock_path, exclusive=True)`：读写都用真实文件锁而非信任 SQLite，因为同一台机器上可能有 Streamlit 进程与计划任务脚本**两个进程**并发读写同一 CSV（Windows 占位锁下这一保护不存在，见潜在错误）；
- 第 96 行 `os.replace(temp_path, file_path)`：同目录内替换，保证原子性（跨盘符会退化为 copy）；
- SQLite UPSERT 的 `ON CONFLICT(symbol, source, data_type, period) DO UPDATE`：同名数据集重复保存只更新一行，不会膨胀；
- 写库失败时 `os.replace(backup_path, file_path)`（第 134 行）还原旧 CSV；若此前文件不存在则删除新文件——**不留半成品**。

`load_dataset`（第 147 行起）的一个细节：文件缺失但状态为 success 时返回 `(None, meta)` 而不是抛异常——调用方可以展示"缓存时间戳存在但数据丢失"的明确状态，这正是第二章末尾排错案例能被诊断的原因。

`core/indicators.py` 全文 13 行，就是 `add_ma20`：`rolling(20).mean()` + `(close-MA20)/MA20*100`。它是全系统最小编程单元，供旧页面使用；新代码多用 `services/index_signals.py` 的带历史转变日期版本（第 10 章）与 `services/ma_timing_core.py` 的统一状态机（第 9 章）。

## 潜在错误

1. **Windows 占位锁**：`fcntl` 守卫（工作区未提交修改）让 Windows 原生 Python 可以运行数据层，但 `_dataset_lock` 在 Windows 上是**空操作**——多进程并发写同一 CSV 的保护失效。单进程 Streamlit 部署可接受，若未来在 Windows 上同时跑脚本与页面，需要补 `msvcrt.locking` 分支。
2. **绝对路径入库**：`datasets.file_path` 存绝对路径，换机器/换目录后旧元数据全部失效，`load_dataset` 返回 `(None, meta)`，需要重新拉数或手工改库。
3. **守护脚本仍顶层 `import fcntl`**：`scripts/update_index_ma20_scheduled.py`、`monitor_iron_ore_price.py`、`monitor_position_timing_trades.py` 没有 `core/cache.py` 这样的守卫，Windows 原生 Python 下直接崩溃（设计上它们经 `wsl.exe` 桥接，但桥接断链时错误不显式）。
4. **备份文件遗留**：`finally` 里 `backup_path.unlink(missing_ok=True)` 会删掉备份——若进程在"备份已建、替换未做"之间被 kill，下次运行不会复用备份，数据仍是旧的（可接受，无损坏）。
5. `sqlite3.connect(DB_PATH, timeout=30)` 无 WAL 模式，Streamlit 与计划任务并发写时偶发 `database is locked` 风险（timeout 缓解但不消除）。

## 改进方法

- `import fcntl` 移入 `_dataset_lock` 内部并做平台分支（Windows 用 `msvcrt.locking` 或干脆退化为无锁+原子替换），让数据层可移植；
- `file_path` 存相对 `RAW_DIR` 的路径，读取时再拼接，彻底解决迁移问题；
- 打开 WAL：`conn.execute("PRAGMA journal_mode=WAL")`；
- 为 `jobs` 表加索引与自动清理（当前只 `ORDER BY id DESC LIMIT ?`，表会无限增长）。

## 实际案例

第二章的排错案例完整走一遍：在 WSL 中以仓库为 cwd 运行回测脚本，`load_dataset("fund_close_v2_159201.SZ_forward_additive", "tickflow", "fund_close_raw", "5000_1d")` 返回 `(None, meta)`。按 `load_dataset` 第 155-156 行的分支，只有两种可能：`status != 'success'`（查库为 success）或 `Path(file_path).exists()` 为假。打印 `file_path` 得 `C:\Users\Renne\investment_dashboard_data\data\raw\tickflow\fund_close_v2_159201.SZ_forward_additive_5000_1d.csv`——Windows 路径在 WSL 里自然不存在。解决：包装 `load_dataset`，失败时按 `RAW_DIR/source/{symbol}_{period}.csv` 重读。这个案例说明：**元数据里的绝对路径 + 跨平台运行 = 缓存整体"失明"，但数据毫发无损**。修复脚本后，14 只 ETF 全部命中，才有了全书引用的真实回测数字。

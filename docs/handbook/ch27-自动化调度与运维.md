# 第二十七章 自动化调度与运维

## 理论

个人系统的自动化运维有三个约束：**没有运维团队**（一切要自愈或显式报警）、**没有服务器预算**（跑在本机/WSL + Windows 计划任务）、**没有冗余**（数据坏了只能重拉）。本项目的调度设计围绕这三个约束展开：单实例锁防重入、幂等更新防重复、退出码约定给监控留钩子、dry-run 模式给调试留后门。

## 数学原理

调度正确性的核心是**幂等性**：$f(f(x)) = f(x)$。本项目的幂等链：

- 更新幂等：`find_pending_post_close_index_names` 只返回有缺口的指数 → 无缺口零网络；
- 导入幂等：结单 sha256 不变即 skip；
- 告警幂等：边沿触发状态机（第 26 章）；
- 通知幂等：slot 去重（`notified_slots`）；
- 缓存短路幂等：`use_fresh_cache=True` 且今日已更新 → 直接返回。

计划任务每分钟/每 30 分钟拉起都安全，因为每一层都是"无事可做就退出"。

## 当前项目实现

### 调度矩阵

| 任务 | 触发 | 脚本 | 关键机制 |
|---|---|---|---|
| 指数正式数据 | 每天 15:10、16:10（上海） | `update_index_ma20_scheduled.py` + `install_index_ma20_update_tasks.ps1` | pending 判定、`use_fresh_cache=False`、退出码 0/1/2 |
| 铁矿石价格告警 | 每分钟 | `monitor_iron_ore_price.py` + `install_iron_ore_price_alert_task.ps1` | 交易时段过滤、边沿触发、730 元阈值 |

Windows 计划任务 → `run_*.ps1` → `wsl.exe -d Ubuntu -- /bin/bash -lc "... exec .venv/bin/python scripts/xxx.py"`（并 unset 代理、export HERMES_SEND_BIN）——**Windows 是闹钟，WSL 是引擎**。

### 任务与数据页（pages/9_任务与数据.py，153 行）

手动更新的两段式确认：

1. 点"更新缺失的正式指数数据" → `build_pending_index_update_preview`（**纯本地缓存检查，不联网**）→ 预览表（指数/目标交易日/缺失交易日/待更新原因/主更新源/复核源）；
2. 点"确认更新并复核" → **再次**重建 preview 并用行级签名对比——若调度器在两次点击之间已补数，签名变化则要求重新确认（**TOCTOU 防护**）→ 一致才执行 `run_index_ma20_update(use_fresh_cache=False)` + `verify_updated_index_data`（独立源复核 ±0.20%，只读）→ 结果展示。
3. 下方 `list_datasets()` / `list_jobs()` 的数据集与任务浏览。

### 单实例锁

`fcntl.flock(LOCK_EX|LOCK_NB)` 非阻塞拿锁，拿不到 yield False 直接退出——三分钟内两个计划任务实例只有一个干活。锁文件在 `output/locks/`。

## 代码分析

`run_scheduled_update` 的退出码语义（`update_index_ma20_scheduled.py`）：

- `0`：无 pending 或全部补齐；
- `1`：更新调用失败；
- `2`：更新执行了但**仍有缺口**（remaining 非空）——这是最有价值的退出码：任务"成功"但没干完活，监控若只看 exit=0 会漏报，需要区分"没干活"与"没干完"。

`build_pending_index_update_preview` 的行级签名（`_preview_signature`）：把每行 tuple 成 `(指数, 目标交易日, 缺失交易日, 待更新原因, 主更新源, 复核源)` 的列表——任何字段变化（哪怕只是原因措辞）都会让签名不同，保证"确认的内容 = 执行的内容"。

`scripts/migrate_fund_price_caches.py` 的限频处理：正则解析"请求频率超限.*?请 (\d+)ms 后重试"，等待 `max(ms/1000+1, 6.2)` 秒——**从错误消息里提取退避参数**，比固定 sleep 更尊重服务端指令。

## 潜在错误

1. `import fcntl` 顶层：全部调度脚本 Windows 原生不可运行（依赖 wsl.exe 桥接）——桥接断（WSL 发行版更名/卸载）时计划任务静默失败，只有任务计划程序里的最后运行结果可查；
2. 调度脚本无 StreamHandler：`logging.info` 只进文件（`output/logs/`），控制台/任务计划看不到过程；
3. 锁文件无陈旧清理：进程被 kill -9 后锁自动释放（flock 随 fd 消失），但锁文件常驻——无实害，仅目录整洁问题；
4. 15:10/16:10 是固定时刻：若 16:10 时港股结算价未出（极端延迟），当轮直接退出等下一日——无第三轮兜底；
5. `update_microcap_snapshot.py` 与页面同时写快照缓存靠线程锁（`_CACHE_WRITE_LOCK`）——**进程间**并发仍靠 `core.cache` 的文件锁，依赖两者都走 `save_dataset`（当前满足）。

## 改进方法

- 计划任务桥接脚本加"WSL 存活预检"（`wsl -l -v` 失败时写 Windows 事件日志或落一个 FAIL 文件）；
- 调度脚本加可选 `-v` 开关挂 StreamHandler；
- 16:10 之后再加一个 20:00 的兜底轮（覆盖港股/美股延迟出数）；
- 退出码 2 时在 `output/` 落 `pending_summary.json` 供外部监控轮询。

## 实际案例

一天的真实运维时间线（全自动化，无人值守）：

```
21:00-23:00  铁矿夜盘时段，脚本每分钟检查（开市内则抓价比对 730 阈值）
09:15        首个交易提醒槽位前，页面若被打开则缓存优先渲染昨日正式数据
09:30-15:00  持仓页 fragment 按带调度（第 13 章），5 个提醒槽位各自独立运行
15:05        页面收盘确认链启动（若页面开着）
15:10        指数计划任务第 1 轮：pending = A股+日盘期货+已收盘市场 → 补齐
16:10        第 2 轮：补港股 + 重试缺口；退出码记录当日是否补完
任意时刻     月结单到达 → 打开期货实盘页自动 sync（hash 未变 skip）
```

故障注入测试的真实行为：手动杀掉 15:10 的 wsl 进程 → 当日 A 股缺口未补 → 16:10 第 2 轮 `find_pending_post_close_index_names` 仍能发现缺口（pending 判定不依赖上一轮状态）→ 补齐。**唯一无法自愈的场景是两轮全挂**——这时"任务与数据"页的手动两段式更新就是人工兜底入口，预览签名机制保证人工操作与自动补数的语义完全一致。

# 第二十六章 风险管理、通知体系与告警脚本

## 理论

这个系统的风险管理不靠一个"风控模块"，而是**分散在各层的结构性约束**：

1. **仓位层**：MA 择时天然的风险预算——空仓即 0 风险暴露；半仓策略给 50% 下限；512890 停车把空仓现金转入低波动资产（风险从"股市 beta"降为"红利低波 beta"）；
2. **数据层**：复核容差 ±0.20%、append-only、收盘确认——错误数据进不了决策链；
3. **执行层**：预判的"先卖后买"顺序、整手取整、费用显式——执行偏差有界；
4. **监控层**：铁矿石价格告警、交易提醒推送、通知引擎——异常要能找到人；
5. **元风险层**：冻结参数、样本外跟踪、`缓存待校验` 时抑制信号——策略自己不可信时系统先停。

## 数学原理

### 阈值带作为风险预算

MA 带宽 $\theta$ 与年换手 $k$ 的关系决定了**执行风险预算**：每笔交易的往返成本 $\approx 2c + \text{滑点}$，年成本拖累 $\approx k(2c+s)$。参数表的隐含选择（159552 用 2.5% 宽带、513310 用 0.5% 窄带）本质是在"whipsaw 损耗"与"确认延迟损耗"之间按各资产波动率分配预算。回测给出的实证（第 9 章表）：宽带的收益不一定更高，但 MDD 一致更浅——**带宽的第一功能是回撤控制**。

### 边沿触发告警

铁矿石告警（`price_alerts.process_price_alert`）是经典**边沿触发状态机**：

$$\text{状态} \in \{\text{normal, alerted, below\_suppressed, rearmed}\}$$

仅在 `不低于 → 低于` 的**上跳沿**推送一次；持续低于不重复（below_suppressed）；回升后重新武装（rearmed）。状态文件 `output/alerts/iron_ore_below_730.json` 原子写（tmp+replace），进程重启不重置——防止"每分钟计划任务 = 每分钟一条微信"的告警风暴。**SendKey 永不入库不入日志**（异常信息只记 `type(exc).__name__`，因为请求异常的 URL 可能带凭证）。

### 通知引擎的通道回退

`notify.engine.send` 的 AUTO 解析：微信类按优先级回退链 **ServerChan → PushPlus → WeCom**（取第一个已配置的）；ntfy 已配置则追加；`priority ≥ HIGH` 自动追加 Windows Toast。每次发送写 SQLite 历史（`output/alerts/notifications.db`）。

## 当前项目实现

### price_alerts.py（214 行）

`process_price_alert(*, price, threshold=730.0, contract, checked_at, state_path, notify)` → `PriceAlertResult(frozen: status/message/notified/below_threshold)`；`send_hermes_weixin_message` 调 `~/.local/bin/hermes send --to weixin --json`（timeout=60，校验 JSON `success`）；`serverchan_endpoint` 自适应 sctp 新端点（`https://{num}.push.ft07.com/send/{key}.send`）与旧 `sctapi.ftqq.com`。

### scripts/monitor_iron_ore_price.py（169 行）

计划任务每分钟拉起 → flock 单实例 → 非交易时段/非夜盘直接跳过（`_futures_market_is_open("I0")`）→ 复用 `index_realtime._fetch_futures_quote("铁矿石主连","I0")` → 合约名每 30 分钟整点才重解析（`now.minute % 30 != 0` 用缓存）→ `--test-price` 用 **TemporaryDirectory** 里的临时状态文件（不污染真实告警状态）→ `--dry-run` 只打印比较。

### notify/ 包（5 文件，~800 行）

models（Priority/ChannelType/NotificationMessage）→ channels（ServerChan/Ntfy/PushPlus/WeCom/WindowsToast 五通道，异常全部转失败结果不抛出）→ engine（AUTO 解析 + SQLite 历史）→ server（FastAPI ntfy 兼容网关，`POST /{topic}`，**无鉴权**——仅限本机使用）。`send_trade_signal` 的动作→emoji 映射（买入📈/卖出📉/转入512890 🛡️）与 A 股红涨的语义一致。

### 交易提醒（monitor_position_timing_trades.py，第 13 章已述）

`format_notification` 的失败语义：**errors 时不发买卖建议**（"ETF均线策略提醒失败 {slot}"）——宁可没提醒，不给错提醒。

## 代码分析

`process_price_alert` 的状态转移表（值得整段抄进自己的工程笔记）：

| 当前态 | 本轮价格 | 动作 | 下一态 |
|---|---|---|---|
| 正常/未告警 | < 阈值 | **推送** | alerted |
| alerted/below_suppressed | < 阈值 | 不推 | below_suppressed |
| 任意 | ≥ 阈值 | 不推 | rearmed（重新武装） |

`--test-price` 的隔离：临时 state.json + 标题加【模拟告警】——测试链路完整但零副作用，这是告警脚本应有的自我修养。

`WindowsToastChannel` 的实现细节：PowerShell 执行 WinRT Toast 脚本、正文截 120 字符、**转义只处理双引号**——标题含 `$`/反引号/尖括号时可能破坏 PowerShell/XML（潜在注入点，个人设备风险可接受但要知道）。

## 潜在错误

1. `price_alerts` 标题硬编码"铁矿石主连跌破 X 元/吨"——模块名是通用的 PriceAlert，实现只服务铁矿石场景；
2. WindowsToast 的转义不完整（上文）；
3. PushPlus 通道用 **http** 而非 https（token 明文过网）；
4. ntfy 公网主题（ntfy.sh）无鉴权，`NTFY_TOPIC` 在 engine 路径下被 message.topic 覆盖（"alerts"/"trades"）——任何人可订阅你的告警；
5. engine 的 `alert_state` 表建而未用——去重状态预留给表但引擎不读它；
6. 交易提醒脚本 `state.notified_slots` 单通道失败也标记已通知（不重试）。

## 改进方法

- `price_alerts` 参数化标的与标题模板；
- WindowsToast 用 `html.escape` + `shlex.quote` 双重转义或改走 `win11toast` 库；
- PushPlus 切 https；ntfy 加 basic auth 或自托管；
- 通知失败时回滚 slot 标记（见第 13 章）；
- 把 `alert_state` 表接入 process_price_alert（跨脚本共享状态，替代 per-script JSON）。

## 实际案例

把 5 号风险层（元风险）的真实机制走一遍：某日 TickFlow 返回的 512890 前加复权历史出现回溯变化（分红未入缓存时增量抓取的典型症状）→ `load_or_fetch_etf` 检出 overlap changes → 全量重建；若重建失败（网络/限频）→ 状态"缓存待校验"、`formal_history_valid=False` → 下游全部静默降级：择时表该行消失、512890 停车快照占位、50 万策略报错停止、交易提醒脚本 `format_notification` 走 errors 分支**只发"提醒失败"不发建议**。整个链条没有任何一步"用旧数据凑合出信号"——**系统的最后防线是"我不确定的时候我拒绝说话"**，这是个人量化系统里最难写也最值钱的一行代码。

# 第六章 只追加历史与更新编排：index_update_* 与定时任务

## 理论

行情历史的价值在于**不可变性**：一旦某天的收盘价被缓存，它就是计算 MA20、回撤、区间收益的"宪法"。任何"顺手刷新一下"都可能把盘中值、错误值写进去，且事后无法察觉。本项目的答案是把缓存分成**四层**：

| 层 | source 名 | 语义 | 写入方式 |
|---|---|---|---|
| 累计原始 | `index_history` | 全量原始日线（可能含盘中旧值） | append-only |
| 收盘确认 | `index_final_history` | 已完成交易日的正式收盘 | append-only |
| 源校正 | `index_source_correction_history` | 从 `source_correction_start` 起的更正行 | append-only |
| 长历史 | `index_long_history` | 每指数最长研究历史（≤20000 bar） | append-only |

计算时用**叠加（overlay）**：`effective = history ←overlay← finalized ←overlay← correction`——后层同日覆盖前层，但只发生在内存，任何一层原始行都不被改写。这等价于数据库的"事件溯源 + 物化视图"：历史不可变，视图可重建。

## 数学原理

缺口检测的判据是**交易日集合差**。设最近 $W=20$ 个交易日（按市场日历生成）为 $S_W$，有效历史日期集合为 $D$，则待补集 $M = S_W \setminus D$，增量拉取窗口放大为

$$\text{days} = (T - \min M).\text{days} + 14$$

（+14 天缓冲覆盖节假日与源延迟）。Bootstrap 条件：$|D| < 252$ 时拉 `days=1000`（TickFlow 路径为 1000 bar）——252 是一年交易日数，保证 MA20 状态转变统计不建立在短窗之上。

独立源复核的判定：$\varepsilon = |P_{\text{verify}} - P_{\text{formal}}| / |P_{\text{formal}}| \times 100\% \le 0.20\%$ 记"一致"。

## 当前项目实现

### 编排主流程（index_update_orchestration.py）

`run_index_ma20_update(api_key="", days=120, cache_source="auto", use_fresh_cache=True, progress_callback=None, market_names=None, index_names=None, max_workers=4) -> UpdateResult`：

1. `start_job` 落库任务记录；
2. **今日缓存短路**：`use_fresh_cache=True` 且 `("index_ma20_latest", ...)` 报告的 `last_update_time` 是今天且全部满足 `has_current_index_quote` → 直接返回，零网络；
3. 先并发刷新期货**当前具体合约**日线（`refresh_futures_current_contract_histories`）；
4. `ThreadPoolExecutor(max_workers=4)` 并发跑 `fetch_index_report`（每指数）；
5. 异常降级：抓取失败时读本地缓存 + `refresh_cached_eastmoney_index_report`（东财列表最新价），够新才 `persist_confirmed_index_report_row` 固化目标日行；
6. `merge_index_report`（existing 优先、选中指数 update 优先）→ `enrich_index_report_indicators` → `sanitize_index_report_market_dates`（非交易日置 NA）→ `trim_index_report(120)` → `save_dataset("index_ma20_latest", ...)`——**唯一整文件覆盖写**；
7. `finish_job` 收尾。

### 单指数管线（fetch_index_report）

读取三路缓存 → overlay → 缺口判定（20 交易日 / 252 行 bootstrap）→ TickFlow 主路径（`fetch_count = 1000 or 30`）→ 仍不够新则 `fetch_one_index`（TickFlow 优先 → 路由器 10 种源）→ `filter_completed_market_dates` 剔除未收盘当日行 → `append_cached_index_rows` 写三处缓存 + `sync_index_long_history`。

### append-only 的实现（index_update_persistence.py）

```python
def append_cached_index_rows(old_df, new_df):
    unseen = new_df[~new_df["trade_date"].isin(old_df["trade_date"])]
    merged = pd.concat([old_df, unseen], ignore_index=True)
    return merged if len(merged) > len(old_df) else None   # 行数不增不写
```

`sync_index_long_history` 有个保守设计：长历史缓存为空时直接 return 不初始化——长历史必须由显式 bootstrap 流程创建。

### 验证（index_update_validation.py）

`verify_updated_index_data(index_names, target_dates, api_key, max_workers=4, tolerance_pct=0.20)` 只读不写：正式价取 `index_final_history` 目标日行，复核源选择规则——有 api_key 且有 `tickflow_symbol` → 用配置 source 拉同日；VIX 强制 `^VIX`、恒生科技强制 `^HSTECH`；HSHYLV → 恒生官网单行；否则"暂无独立日线复核源"。

### 定时任务（scripts/update_index_ma20_scheduled.py）

- `fcntl.flock` 单实例锁（`output/locks/index_ma20_scheduled.lock`）；
- pending 判定 = `find_pending_post_close_index_names()`（正式缓存 < 目标日 ∨ 20 日缺口 ∨ 校正层未到目标日）∪ `find_pending_futures_current_contract_index_names()`；
- **强制 `use_fresh_cache=False`**（绕过"今日缓存短路"，否则补数会被短路跳过）；
- 退出码：0=无缺口，1=更新失败，2=仍有缺口；
- `--dry-run` 只读缓存列 pending。
- Windows 侧通过 `install_index_ma20_update_tasks.ps1` 装 15:10/16:10 两个计划任务，经 WSL 调用。

## 代码分析

`fetch_index_report` 中 TickFlow 路径的一个精妙处：拉回的 raw 先 `filter_completed_market_dates`（剔除盘中当日行）再**分别增量 append 到三处缓存**（finalized / tickflow / index_history），三处都判 `len > previous` 才写。这意味着：同一次抓取结果，收盘确认层只收已结算日，原始层可能多收一天——两层的"最新日"可以不同，这正是设计意图。

`has_current_index_quote`（index_update_frames.py）用的是**默认参数版** `latest_settled_trade_date`（无 10 分钟延迟），而编排层 `_daily_update_target` 用带 10 分钟延迟版——收盘后 10 分钟内，前者可能已认为"够新"，后者才把今天当目标日。两者口径轻微不一致，属于已知的保守错位（宁可少更新一次）。

## 潜在错误

1. **重复网络请求**：tickflow 成功但 stale 且有缺口时，会先 `fetch_index_from_source` 再进 `fetch_one_index`（内部又拉一次 TickFlow），同一次更新可能对同一指数拉两遍；
2. tickflow 路径整体被 `except Exception: df = None` 吞掉，无日志——主源静默失败只能靠复核层事后发现；
3. `sync_index_long_history` 空缓存不初始化：如果长历史缓存被误删，该指数的长历史将永远停止增长（详情页仍可用 `fetch_index_history(days=10000)` 现拉）；
4. 定时脚本 `import fcntl` 无容错，Windows 原生 Python 不可运行（与 core.cache 同款约束）；
5. `merge_index_report` 的 `prefer_update_index_names` 集合外指数"existing 优先"——若某个未选中指数在缓存中是错的，普通更新不会修正它，必须显式点名。

## 改进方法

- 给 tickflow 路径的 `except` 加 `logger.warning` 与计时，让主源故障可见；
- `sync_index_long_history` 空缓存时回退用 `index_history` 初始化（保留 append-only 语义）；
- 把 `has_current_index_quote` 统一改为带 10 分钟延迟口径，消除两处判定的错位窗口；
- 在 `verify_updated_index_data` 结果上追加"自动重试一次复核超差的指数"开关（当前只报告，不重试）。

## 实际案例

本地缓存（Windows 运行时目录）给出了这套机制的真实快照：`index_final_history` 中 `000001.SH` 有 **1000 行**（bootstrap 上限）、最新日 2026-08-14；`index_raw_980092.SZ_1d.csv` 有 664 行（2014-01-02 起的国证官方历史，对应 AGENTS.md 要求的"基日回溯 2012-12-31"策略由 `index_hist_cni` 提供更早数据，此处从 2014 年起是 `index_history` 层的 TickFlow 路径产物）；`恒生港股通高息低波` 只有 1 行（见第五章案例）。`index_ma20_latest` 展示缓存 84 行（约等于 120 自然日内的交易日数），`last_trade_date=2026-08-14`——正是"只追加的原始层 + 覆盖写的展示层"两层结构在磁盘上的样子。

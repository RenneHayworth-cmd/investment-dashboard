# 第二十三章 期货实盘（上）：月结单解析、持久层与对账

## 理论

期货账户的数据源是**券商月结单**（客户交易结算月报），它有三个特质：官方（数字以它为准）、月度（月中没有逐日权威数据）、不完整（期权不开平标志、无逐日盯市）。`期货实盘` 页的架构就是围绕这三个特质设计的：

- 月结单 = **正式账户快照 + 不可变执行历史**（每次导入都保留）；
- 月末之后的成交/出入金 = **手工记录**（可删、可对账、可被后续结单"接管"）；
- 一切歧义 → `待核对` 标记 + 人工裁决，绝不猜。

## 数学原理

### 对账的匹配代数

手工成交 $m$ 与月结单成交 $b$ 的匹配候选集：

$$C(m) = \{b: \text{broker\_id}(m)=\text{broker\_id}(b)\} \;\cup\; \{b: (date, type, contract, side, |p_m - p_b| < 10^{-7}, q_m = q_b [, time]) \text{ 全等}\}$$

判定：$|C| = 1$ → **已接管**（正式数据取代手工）；$|C| \ge 2$ → **待核对**（排除出计算，等人工）；$|C| = 0$ → 保持手工（月末后真实成交）。资金流水同构（仅对 `flow_date ≤ 最新月末` 的行对账）。**容差 0.05 元**（`RECONCILIATION_TOLERANCE`）是全系统对账的统一尺度。

### 手工录入的合法性约束

- 时间：必须 **晚于最新月结单末**（`statement_end + 1 天` 起）；
- 平仓上限：模拟应用后可平量不足 → `ValueError("... {side}仓最多可平 {available} 手。")`，事务式回删；
- 乘数：无法从成交额反推且台账未知 → 拒绝录入（"无法确认合约乘数，请填写成交额或权利金。"）。

## 当前项目实现

### 文件发现与解析（futures_live_models.py + statement_parser.py，571 行）

- 匹配 `^\d+_(\d{4}-\d{2})\.(xls|xlsx)$`，**只认券商结单命名**，衍生统计簿不进输入；
- 默认目录 `DEFAULT_FUTURES_STATEMENT_DIR`（WSL OneDrive 路径）→ `FUTURES_STATEMENT_DIR` 环境变量 → 页面输入；Windows 盘符自动改写成 `/mnt/x/`（**设计运行于 WSL**）；
- 账户表 14 个标签字段（上月结存→追加保证金，`风险度` percent=True 自动除以 100）；
- 期货持仓：小节"期货持仓汇总"，多/空拆两行，**保证金只记到一行**（`margin if side=="多" or long==0 else 0`，防重复计）；乘数反推 `|浮盈|/(|今结算-均价|×手数)` 且误差 ≤0.05 才接受；
- 期权成交：**`open_close 恒为"未提供"`、close_pnl=None**（券商不提供）——衍生盈亏改用第 24 章的现金流量法；
- 资金流水：出入金明细（每行拆入/出两条，`source_key=f"{file}|cash-{n}-{type}"` UNIQUE）+ 其它资金明细（跳过"交易手续费"，分类为 申报费/行权手续费/账户费用）；
- **申报费**：从流水汇总写入 `account["declaration_fee"]`（结算单另一处独立解析 `_parse_declaration_fee` 是未被调用的死代码）；
- 四组对账校验（容差 0.05，产 warnings）：月手续费 vs（成交费+申报费+账户费用）；逐日出入金 vs 当月存取合计；账户浮盈 vs 持仓浮盈合计；账户保证金 vs 持仓保证金合计。

### 持久层（futures_live_repository.py，763 行）

- `sync_statements(directory, force=False)`：逐文件 sha256 比对（未变且成功则 skip）→ `SAVEPOINT import_statement` 包裹导入 → 失败回滚记"失败"（**首次失败才写导入记录**）→ 统一跑 5 个 reconcile/backfill；
- 重导按 `source_file` 先 DELETE 旧的 4 类行再重插（幂等）；
- `_reconcile_manual_trades / _reconcile_manual_cash_flows / _reconcile_option_expiry_events`：先全部重置为'手工'再逐条匹配（**每次同步全量重对账**，删除结单也能正确降级）；
- 手工 CRUD：`add_manual_trade / add_manual_cash_flow / add_manual_daily_pnl / resolve_manual_daily_pnl` 及对应 delete（仅'手工'态可删）；
- `_effective_*` 计算口径：官方 + 未接管且晚于月末的手工——**已接管的手工行从计算中排除**（它已是正式数据的重复）。

## 代码分析

重导幂等的设计链：文件 hash 进 `futures_statement_imports`（`file_path UNIQUE`）→ 未变 skip；变了（券商可能改发更正版）→ SAVEPOINT 内删除重插 → 全量重对账。**"删了重插"保证结单修正不产生幽灵行**；"全量重对账"保证手工行的接管状态永远反映当前结单集合。

乘数反推的三重防御（持仓 + 成交 + 台账中位数回填 `_backfill_position_multipliers`）：反推失败不猜、录入时强校验、历史缺口用同合约成交乘数**中位数**回填——中位数而非均值，抗单条异常。

期权行权手续费掩码 `exercise_fee_mask`：`entry_type=="行权手续费"` **或** notes 含"行权手续费"——兼容旧版本把行权费导成"账户费用"的历史数据，一个谓词救回一类账。

## 潜在错误

1. **同月双文件孤儿**：`futures_account_monthly` 以 `statement_month` 为 PK `INSERT OR REPLACE`，而行删除按 `source_file`——两个不同文件声称同一月份时，账户表留 A 文件的、持仓/成交留 B 文件的孤儿集合（个人使用中"券商改名重发"会触发）；
2. 精确匹配容差 1e-7：成交价 0.0001 的浮点差即不匹配 → 多出一条"手工"行 + 结单里同价行 → 双记风险（接管机制靠"唯一候选"防护，但 1e-7 太紧，误配成 0 候选后双记）；
3. `_table_after_header` 遇首个全空行停止——结单表格中间的空行会截断数据（依赖券商不空行）；
4. 保证金对账把期权保证金计入合计，若券商"保证金占用"仅指期货则误报 warning；
5. `_parse_declaration_fee` 死代码仍经 facade 导出，调用它会得到与主流程可能不一致的口径。

## 改进方法

- 重导时按 `statement_month` 也做一次清场（或禁止双文件同月，导入时校验）；手工价匹配容差放宽到 0.001（仍在 0.05 对账容差内）；
- `_table_after_header` 允许连续空行（≤2 行）再停止；
- 保证金对账按 asset_type 分组核对；
- 删除死代码 `_parse_declaration_fee` 或合并进主流程并写测试。

## 实际案例

对账生命周期的一个完整例子：月末后手工录入一笔"2026-09-05 买平 I2609 2 手 @712.0"→ `reconciliation_status='手工'`，参与预计持仓与盈亏。9 月结单到达后同步：若结单里有 `(2026-09-05, I2609, 买, 712.0, 2, 成交序号 X9821)` 且全库唯一 → 手工行变 `已接管`，`matched_statement_trade_id` 指向结单行，**计算改用结单的官方 fee 与 close_pnl**；若结单里出现两笔同价同量（分仓下单）→ 手工行 `待核对`，从计算中排除，页面标红等人工裁决。整个过程**没有任何一步会修改结单数据**（官方行只读），手工行要么升级为"已被正式数据接管"，要么降级为"待核对"——账本的权威链永远单向：手工 → 正式。

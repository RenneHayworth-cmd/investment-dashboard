# 第十三章 实时刷新调度与收盘确认链：position_runtime / realtime.py

## 理论

实时页面最容易犯的两个错误：**刷太勤**（限频、封号、费用）与**刷不准**（该刷的时候没刷）。本项目的解法是**三层节流状态机**：

```
Streamlit fragment (run_every=120s，全天候重跑)
  → 组件层 session_state band TTL（换日/换带/超时才刷）
    → 服务层进程级 _RUNTIME_ETF_QUOTE_FETCH_STATE（band TTL + 午间单次闸）
```

任一层未到期都不实际联网。时段带（band）与 AGENTS.md 的调度表一一对应：早盘 9:30-10:00 每 10 分钟、上午 10:00-11:30 每 30 分钟、午休抓一次午间收盘、下午 13:00-14:50 每 30 分钟、尾盘 14:50-15:00 每 2 分钟、15:05 后转入"收盘确认"模式。

## 数学原理

调度的核心是**TTL 判定**的布尔式：

$$\text{due} = \text{换日} \vee \text{换band} \vee \text{scope未覆盖} \vee \text{无上次尝试} \vee (\neg\text{午间已成功} \wedge \Delta t \ge \text{TTL})$$

其中 band 由当前时刻决定：

| 时段 | band | TTL |
|---|---|---|
| 9:30–10:00 | early | 600s |
| 10:00–11:30 | midmorning | 1800s |
| 11:30–13:00 | lunch | 600s + 单次成功闸 |
| 13:00–14:50 | afternoon | 1800s |
| 14:50–15:00 | realtime | 120s |
| 其余 | None | 不联网（只渲染缓存） |

**失败也计入节流**：`fetched_at` 在失败时同样更新，下一次尝试要等完整 TTL——这是"失败退避"的简化实现，防止数据源故障时页面变成 DDoS 机。

收盘确认链的时间窗：`etf_intraday_quote_ready()` = 交易日 9:30 ≤ t < **15:05**（注意上界是 15:05 而非 15:00，为"收盘待确认"保留 5 分钟窗口）；`etf_final_close_ready()` = t ≥ 15:05。尾盘报价保留窗口 `is_close_retention = t ≥ 15:00`（无上界，靠 quote_time 为当天约束失效）。

## 当前项目实现

### 会话判定（position_sessions.py，183 行）

八个布尔函数全部基于 `market_calendar.get_market_window("A股")`，常量在 `position_models.py`：`ETF_FINAL_CLOSE_READY_TIME=15:05`、`ETF_MORNING_TIMING_REFRESH_SECONDS=600`、`ETF_MIDSESSION_TIMING_REFRESH_SECONDS=1800`、`ETF_REALTIME_TIMING_REFRESH_SECONDS=120` 等。

### 运行时行情层（position_runtime.py，457 行）

- `refresh_runtime_etf_quotes(codes, *, api_key, market_now)`：锁内判 due；午间特判 `lunch_already_succeeded`（当天午间带一旦成功本带内不再拉）；先写 `last_attempt` 再**锁外**调网络（不持锁做 IO）。
- `fetch_tickflow_etf_quotes`：**每批 5 只**调 `client.quotes.get`；丢弃 `quote_time` 日期 != 当天的行；161128 缺失时新浪兜底；全空抛 ValueError。
- `apply_etf_realtime_quote_to_timing(item, quote, ...)`（预览核心）：把当日 quote 作为临时行**追加**到正式历史尾部（去掉今天的正式行），调 `calculate_etf_timing_snapshot` 现算——**预览信号 = 正式历史 + 当日瞬时价**，分母是完整历史；512890 无策略时只套价格不套信号（停车卡片要用同源瞬时价）。

### 组件调度状态机（components/position/realtime.py，545 行）

`render_etf_timing_section_impl` 的 14 步流程（摘要）：正式基线（纯缓存）→ 15:05 自动确认（10 分钟重试强刷 stale ETF）→ 预览行情装载 → 衍生品刷新请求 → 早盘带 → 午间/下午带 → 尾盘带 → 收盘保留窗口 → 衍生品实时预览（`version=3` 状态升级强制重取）→ 卡片合成 → caption → 渲染 → 操作指引（永远只用正式日线）→ 50 万策略绩效（实时价只做临时估值）。

### 计划任务提醒（scripts/monitor_position_timing_trades.py，375 行）

五个槽位 `((9,45),(11,45),(14,45),(14,50),(14,54))`；`build_position_timing_trade_preview` 对比**正式目标持仓 vs 盘中预判持仓**的净差生成行动清单（先卖后买）；14:50 首档"无需操作"后抑制后续 no-action 通知；ServerChan + Hermes 双通道并行，单通道失败不阻塞。

## 代码分析

**收盘确认链**是本章的灵魂，完整路径：

1. 15:00-15:05：尾盘最后报价以"收盘待确认"状态显示（`allow_close_retention=True`，source 文案"TickFlow当天最后行情（待正式收盘确认，不写入缓存）"）；
2. ≥15:05：`etf_final_close_ready` → fragment 内对 stale ETF（latest_date < 目标日）逐只 `load_or_fetch_etf(force_refresh=True)`，session 键 `position_etf_auto_final_last_attempt` 以 600s 节流——**反复强刷直到每只都追上目标日**；
3. 追上后 `formal_close_missing=False` → 清空所有预览行情 → 卡片与择时表切换为正式数据；
4. TickFlow 若 15:05 仍没出收盘价，`_append_sina_final_close`（161128 专用）用新浪收盘快照补；其余标的等下一轮 600s 重试。

两个"两层节流"的精细处：

- **组件层先判、服务层再判**：组件层 band TTL（如 early 600s）到期才调 `refresh_runtime_etf_quotes`，服务层再查自己的 `last_attempt`——双层 TTL 取交集，最坏情况刷新间隔是两层之和的一半，实际取 max 效果；
- **失败保旧值**：任何 band 抓取失败都保留 `previous_quotes` 并写 error，`fetched_at` 更新——预览退化为"上一次成功的行情 + 一条错误提示"，永不白屏。

## 潜在错误

1. **失败退避粒度粗**：早盘失败后要等 600s 才重试，期间预览停在开盘前状态——对"想立即重试"的用户无解（只能等或刷新页面重置 session？不，session 也在）。
2. `timing_items` 在多个分支重复计算、后写覆盖先写：尾盘分支与保留窗口分支各算一次，浪费且让"最终显示哪个版本"依赖分支顺序。
3. `missing_realtime_codes` 同样被多分支覆盖，最终值取决于最后进入的分支——诊断信息可能失真。
4. 衍生品 `version=3` 硬编码：改实现必须记得 bump，否则缓存的状态字典按旧结构解析。
5. 计划任务脚本 `state.notified_slots` 在单通道失败时也标记已通知——微信推送失败不会重试。
6. 11:45 槽位处于午休，quote 是上午最后快照，预判基于午前价——语义正确但用户可能以为是"午间收盘后"的判断。

## 改进方法

- 失败退避改为指数化（600s → 120s 首次 → 翻倍），并给 UI 一个"立即重试"按钮（写 session 强制 due）；
- `timing_items` 的计算收敛到最后一步统一执行（分支只决定 quotes 来源）；
- 衍生品 state 的 schema 版本做成自动检测（键集指纹），而非手工 bump；
- 通知失败时把 slot 从 `notified_slots` 移除，下次脚本运行重试。

## 实际案例

以 2026-09-03（周四，真实时间线）复盘一天：

- 09:30-10:00：早盘带每 10 分钟一批（3 批 × 15 只 ETF），卡片与择时预判使用实时价，`状态=早盘预判`；
- 10:00-11:30：每 30 分钟（5 批）；
- 11:30-13:00：**午间只成功一次**（成功后闸门关闭），预览标签"午间预判"一直保留到 14:50；
- 13:00-14:50：每 30 分钟（4 批）；
- 14:50-15:00：每 2 分钟（5 批），`状态=实时预判`；
- 15:00-15:05：保留最后报价，`状态=收盘待确认`；
- 15:05+：自动确认链强刷 stale ETF；缓存当前至 9-02、9-03 尚未收盘，目标日为 9-02 → 无 stale → 不联网，展示正式 9-02 数据。

当天全页带刷新合计 3+5+1+4+5 = **18 次**，每次 15 只 ETF 按 5 只一批拆 3 个请求，约 54 次 API 调用——对比"每分钟全量刷"的 1440 批，节流比 98.75%。计划任务侧，`monitor_position_timing_trades.py` 在 9:45/11:45/14:45/14:50/14:54 五个槽位各自独立运行（Windows 计划任务 → wsl.exe），与页面互不依赖——页面挂了提醒照发。
